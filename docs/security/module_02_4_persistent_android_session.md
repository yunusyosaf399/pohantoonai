# Module 02.4 — Persistent, secure Android authentication

Date: 2026-11-12. Repository: yunusyosaf399/pohantoonai. Existing Supabase project: umlzqlbakfwzgadafhyy.

## Problem and root cause

The user reported that closing/reopening the Android app repeatedly returned them to sign-in.

A verified Flutter startup bug was found: _checkMfaAndRestore incremented the MFA check generation TWICE and set the check/loading flag back to false before the asynchronous result arrived. The check could never complete, so the saved school workspace was not restored. The Auth event listener also restarted this check on every same-user token refresh, creating competing requests.

Supabase Flutter 2.18.3 already supports persistent, rotating refresh-token sessions through LocalStorage. We preserve this behavior and move Android's session value into encrypted storage.

## Changes

1. The Supabase client now explicitly has persistSession=true and autoRefreshToken=true. The app NEVER stores passwords, service-role keys, custom JWTs or tokens in school database tables.
2. New AndroidSecureSessionStorage (lib/features/auth/data/secure_session_storage.dart) uses Flutter Secure Storage 9.2.4 with Android Keystore-backed EncryptedSharedPreferences. One-time migration loads and verifies the existing Supabase Flutter SharedPreferences session BEFORE deleting the previous copy.
3. On Android, the manifest now sets android:allowBackup=false so device cloud backup cannot restore encrypted preferences without their original device Keystore key.
4. Existing Web/Windows/Linux/macOS/iOS Supabase SDK persistence is not changed by this Android-specific patch.
5. App startup now checks MFA exactly once per valid identity change, keeps the security loading screen visible until it completes and restores the correct applicant-owned plan, draft and workspace.
6. Same-user tokenRefreshed and userUpdated events do not trigger competing restoration or clear the dashboard. Switching accounts or explicitly signing out still clears previous user data.
7. Transient workspace errors show Retry secure session rather than silently returning to the onboarding wizard.
8. Sign-out clears the encrypted session and any old preferences so it cannot be resurrected later.

## Security constraints

- Long-lived sign-in relies on a rotating Supabase refresh token, NOT a JWT that never expires.
- A revoked, invalid or timed-out session must still require new sign-in.
- An enrolled TOTP user must satisfy the Supabase AAL2 check before the protected school dashboard appears. The database continues to enforce AAL2 through restrictive RLS.
- Recovery-code/link sessions continue to have their own exclusive reset flow, not a normal dashboard login.
- Session data remain local to the Android app install. Uninstall, Clear Storage, or some OS/device recovery scenarios legitimately remove the session.

## Files and tests

- lib/main.dart — fixed MFA check generation and same-user session-event behavior; retry screen
- lib/features/auth/data/secure_session_storage.dart — Android encrypted session and one-time migration
- pubspec.yaml — flutter_secure_storage 9.2.4 pinned (compatible with current Android Java 11 build)
- android/app/src/main/AndroidManifest.xml — cloud backup disabled for Keystore-bound encrypted data
- test/auth/secure_session_storage_test.dart — migration, restart, signout, secure-write failure cases
- test/auth/auth_return_to_dashboard_flow_test.dart — simulated dashboard restart, same-UID refresh, persisted 2FA gate

No SQL migration, new school tenant, or new Edge Function is necessary.

## Physical Android acceptance test

Run from your Pohantoon AI repository:

    git pull --rebase origin main
    flutter pub get
    flutter analyze
    flutter test test/auth/secure_session_storage_test.dart
    flutter test test/auth/auth_return_to_dashboard_flow_test.dart
    flutter test
    flutter devices
    flutter run -d YOUR_ANDROID_DEVICE_ID

Then:
1. Sign in once with Google or a verified email/password account. Complete a TOTP challenge if required.
2. Confirm you reach your saved school dashboard.
3. Swipe the app away from Android Recents WITHOUT clicking Sign out; launch it again. The dashboard should restore directly.
4. After the JWT expires, reopen online. The SDK should rotate the refresh token and preserve the account.
5. Temporarily disconnect the network and reopen. If security/workspace cannot be verified, it should show Retry rather than silently signing out or granting unverified access. Retry when online.
6. Tap Sign out, close/reopen: it must now show Welcome/sign-in.
7. Test the password-reset OTP and two-factor challenge to ensure no bypass.

Avoid uninstalling or clearing app data during the first migration test, as that deletes the very session being tested. Run flutter pub get and commit the regenerated pubspec.lock; it was not generated by the connected environment.
